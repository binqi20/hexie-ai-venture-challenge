# Learning Mall readiness checklist

Version 1.0, October 2026

This checklist supports preparation for Learning Mall distribution. It is not an official Learning Mall submission standard or evidence that publication has occurred. All boxes are deliberately unchecked. Tick an item only after checking the release copy and recording the reviewer, actual date and evidence in the release record.

- [ ] Explain the intended users, five capabilities, three adoption routes and prerequisite venture preparation.
- [ ] Separate the 10 to 15 minute reading estimate from staff preparation time and the 90-minute simulation plus separate defence.

- [ ] Supply descriptive metadata: discipline, resource type, educational use, language, capabilities, delivery mode, access conditions and owner.

## Files and navigation

- [ ] Keep Markdown source editable; provide readable HTML or accessible document exports where needed for the chosen Learning Mall workflow.
- [ ] Supply accessible PDF reading copies only as supplements to editable source files. Check headings, reading order, links and tables after export.
- [ ] Retain YAML persona/scenario sources and the Python prototype files with their README and dependency information; clearly distinguish code from student instructions.
- [ ] Include only the approved release files in any ZIP bundle and inspect it after extraction. Exclude participant data, consent records, private source documents and internal answer keys.
- [ ] Check every path in `07_adoption_kit/adoption_kit_readme.md` against the release package. Treat any missing file as an unresolved release dependency.
- [ ] Test navigation from the uploaded landing page and downloaded pack using the intended reader's access level.
- [ ] Confirm that the prototype's offline demonstration and unconnected LLM stub are described accurately. Do not advertise a functioning LLM service.

## Accessibility and participation

- [ ] Use a logical heading hierarchy, descriptive links, clear table headers and readable contrast; do not communicate distinctions by colour alone.
- [ ] Add useful alt text or equivalent descriptions for images and diagrams. Provide text alternatives to any diagram that does not render.
- [ ] Check keyboard access and reading order in the published format; test the actual exports rather than relying on the source Markdown.
- [ ] Provide captions and transcripts if audio or video is added. No such media is required by this Markdown package.
- [ ] Publish an accessibility note listing tested formats, known limitations and the route to request an alternative.
- [ ] Ensure reviewed text/role-card participation and appropriate defence adjustments preserve opportunities to demonstrate the same capabilities.
- [ ] Keep access needs and support arrangements outside public materials and research datasets.

## Rights and third-party ESG sources

- [ ] Confirm the institutional owner and permitted reuse terms for original project materials; record whether distribution is internal or public.
- [ ] Add a clear licence or permission statement and adaptation attribution instructions once authorised. Do not assign an open licence by assumption.
- [ ] Include this boundary in the release notice: “Original project text paraphrases selected ESG methodology concepts for education. MSCI, FTSE Russell and SASB materials remain third-party sources. Any permission or licence for this kit applies only to material the project is authorised to license. It does not extend to third-party publications, tables or logos.”
- [ ] Verify ESG citations against [REFERENCES.md](../REFERENCES.md); cite relevant industry topics without reproducing provider tables or long extracts.
- [ ] Exclude third-party source PDFs or spreadsheets unless redistribution permission is documented.
- [ ] Check that examples contain no venture letter ratings or claims of third-party endorsement or certification.
